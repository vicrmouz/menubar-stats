# Windows Taskbar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Entregar uma versão portátil Windows 10/11 com CPU/RAM sobre a barra de tarefas e painel semelhante ao macOS.

**Architecture:** Separar núcleo testável de coleta/parsing da interface WPF e integração Win32. Manter fontes Swift existentes independentes. Aplicativo único por usuário, sem modificar o Explorer.

**Tech Stack:** C#, .NET 8, WPF, APIs Win32, xUnit e GitHub Actions Windows.

**Spec:** `docs/superpowers/specs/2026-10-05-windows-design.md`.

## Global Constraints

- Windows 10 e Windows 11; pacote portátil autocontido para Windows x64.
- Faixa de CPU/RAM sempre visível sobre a barra quando esta estiver visível; painel de 300 unidades lógicas, padding 16.
- Sem navegador embutido, injeção de DLLs, alteração do Explorer ou telemetria.
- Sistema a cada 2 segundos, Claude a cada 5 minutos, Codex a cada minuto.
- Tema claro/escuro, múltiplos monitores, DPI e ocultação automática.
- Iniciar com Windows desativado por padrão; configurações em `%LOCALAPPDATA%`.
- Ferramentas nativas Windows; WSL fora da primeira versão.
- Nunca guardar tokens em configurações, testes ou logs.

## Review Focus

1. Arquivos sendo escritos ou removidos: leitura tolerante e atualização seguinte recuperável — tarefa 1.
2. Contadores reiniciados e primeira amostra: taxas não negativas e sem pico artificial — tarefa 2.
3. Reinício do Explorer e troca de monitor/DPI: redescobrir barra e manter faixa/painel na tela — tarefa 3.
4. HTTP lento e encerramento: cancelar trabalho sem bloquear UI nem sobrepor consultas — tarefa 4.
5. Preferências inválidas e atalho de Startup preexistente: defaults seguros e remoção limitada ao atalho próprio — tarefa 5.

## Tarefa 1 — limites locais e HTTP

**Interfaces:** `record LimitWindow(double Percent, DateTimeOffset? ResetsAt)`; `record UsageLimits(LimitWindow Session, LimitWindow Weekly)`; `LimitsParser.ParseCodex(string json, DateTimeOffset now)` e `ParseClaude(string json)` retornam `UsageLimits?`. `CodexReader.Read(string sessionsRoot, DateTimeOffset now)` retorna `UsageLimits?`; `ClaudeReader.FetchAsync(string configRoot, CancellationToken cancellationToken)` retorna `Task<UsageLimits?>`.

- [ ] Criar projetos Core e Tests (`net8.0`) e teste de janela expirada:

```csharp
[Fact]
public void ExpiredCodexWindowIsZero()
{
    var json = """{"payload":{"rate_limits":{"primary":{"used_percent":80,"resets_at":1},"secondary":{"used_percent":20}}}}""";
    var result = LimitsParser.ParseCodex(json, DateTimeOffset.FromUnixTimeSeconds(2));
    Assert.NotNull(result);
    Assert.Equal(0, result.Session.Percent);
    Assert.Equal(20, result.Weekly.Percent);
}
```

- [ ] Executar `dotnet test windows/MenuBarStats.Tests`; confirmar falha pela ausência de `LimitsParser`.
- [ ] Implementar parsing com `JsonDocument`, campos numéricos finitos e percentuais limitados a 0–100. JSON incompleto retorna null. Datas inválidas não impedem percentual válido. Ler JSONL em ordem reversa por evento, com máximo de 512 KB por arquivo; continuar para outros arquivos quando não há evento válido. Ordenar por timestamp do evento quando disponível para evitar escolher arquivo recente com limite antigo.
- [ ] Criar casos de JSON inválido, campos ausentes, linha parcial, múltiplos eventos, arquivo removido durante leitura e janela sem reset; usar diretórios temporários com conteúdo sintético. Consultar os formatos locais sem revelar credenciais reais.
- [ ] Implementar leitura de `.credentials.json` sob `CLAUDE_CONFIG_DIR`/perfil e HTTP via `HttpClient` injetável, timeout de 15 segundos, Bearer e cabeçalho atuais do Swift. Testar 401, JSON inválido, timeout/cancelamento e falta de arquivo por handler HTTP falso. Não modificar credenciais.
- [ ] Executar os testes e registrar o resultado; commit apenas dos arquivos desta tarefa.

## Tarefa 2 — métricas do sistema

**Interfaces:** `Deltas.Cpu(ulong idleDelta, ulong kernelDelta, ulong userDelta)` retorna `double`; `Deltas.Rate(long previous, long current, double elapsedSeconds)` retorna `double`. `SystemReader.Read()` retorna snapshot de CPU, memória, disco e rede.

- [ ] Escrever testes antes do cálculo:

```csharp
[Fact]
public void CounterResetDoesNotProduceNegativeRate()
{
    Assert.Equal(0, Deltas.Rate(1000, 20, 2));
    Assert.Equal(500, Deltas.Rate(1000, 2000, 2));
    Assert.Equal(0.75, Deltas.Cpu(25, 80, 20));
}
```

- [ ] Rodar teste, confirmar ausência da implementação, depois implementar deltas com guards de denominador zero, reset e tempo não positivo. `GetSystemTimes` inclui idle no kernel; subtrair idle do total kernel+user.
- [ ] Criar projeto WPF `net8.0-windows`, `UseWPF=true`, `EnableWindowsTargeting=true`. Implementar P/Invoke de `GetSystemTimes` e `GlobalMemoryStatusEx`, `DriveInfo` do volume do Windows e contadores por interface ativa não loopback. Usar relógio monotônico para deltas de rede e referência por interface.
- [ ] Verificar primeira amostra zero, interface nova/reset, nenhuma interface disponível e falha de disco independente de CPU. Rodar testes e build Windows; commit dos arquivos desta tarefa.

## Tarefa 3 — faixa, posicionamento e painel

**Interfaces:** `Placement.Clamp(double origin, double size, double minimum, double maximum)` retorna posição limitada; `TaskbarHost` fornece retângulo da barra principal e estado de visibilidade em coordenadas físicas. Conversão física/lógica fica na fronteira com WPF.

- [ ] Testar geometria antes da implementação:

```csharp
[Fact]
public void PlacementSupportsNegativeMonitorCoordinates()
{
    Assert.Equal(-300, Placement.Clamp(-100, 300, -1920, 0));
    Assert.Equal(-1920, Placement.Clamp(-2500, 300, -1920, 0));
}
```

- [ ] Executar teste e implementar clamp, incluindo janela maior que a região disponível. Acrescentar casos de quatro bordas da barra e escala 150/200% na conversão de coordenadas.
- [ ] Implementar descoberta Win32 de `Shell_TrayWnd`, região do relógio quando disponível, retângulo por monitor e detecção de janela foreground em tela cheia. Atualizar integração por timer curto e eventos de display; tolerar handle ausente e redescobrir após restart do Explorer. Faixa acompanha visibilidade real da barra em auto-hide.
- [ ] Criar XAML da faixa, tema e painel, seguindo o Swift: ícones vetoriais, fonte 13, números alinhados, padding 16, seções e barras. Janela sem borda e sem botão na taskbar; ocultar durante tela cheia. Permitir arrastar ao longo da barra e limitar posição; clique sem drag abre painel.
- [ ] Implementar fechamento por Escape/perda de foco/clique fora e abertura por Enter/Espaço. Usar nomes acessíveis. Reposicionar painel ao mudar DPI/monitor.
- [ ] Build e inspeção Windows para auto-hide, DPI, Explorer reiniciado e tela cheia. Se não houver máquina Windows, marcar essas verificações pendentes explicitamente; commit dos arquivos da tarefa.

## Tarefa 4 — estado e agendamento

**Interfaces:** `StatsViewModel` implementa `INotifyPropertyChanged`, expõe métricas formatadas, limites opcionais e `RefreshClaudeAsync(CancellationToken)`. `App` possui cancelamento de lifetime e mutex nomeado por usuário.

- [ ] Testar atualização manual concorrente à periódica usando handler HTTP bloqueado: uma consulta ativa por vez; cancelar lifetime termina a consulta. Testar que falha de Claude não cancela updates de sistema/Codex.
- [ ] Implementar loops independentes com `PeriodicTimer`, cancelamento e aplicação do snapshot no Dispatcher. Inicializar dados imediatamente; evitar enumerar sessões ou fazer HTTP na thread UI. Usar guard de consulta Claude e cancelar no shutdown.
- [ ] Conectar ações Atualizar Claude e Sair, mostrar Sem dados na ausência de limites e indicar idade da última atividade Codex. Formats em GB decimais, B/s/KB/s/MB/s e resets relativos em português.
- [ ] Rodar testes e build; testar segunda instância encerrando sem criar outra faixa. Commit dos arquivos da tarefa.

## Registro de execução — 2026-10-05

Código implementado em `windows/`, com núcleo separado, WPF, métricas Win32, painel, limites, preferências, início automático e workflow de publicação. Preferências e o serviço testável de Startup ficaram no núcleo, com adaptador COM na aplicação Windows.

Validação: 33 testes em Release passaram no macOS; WPF compilou sem avisos/erros; publicação autocontida Windows x64 gerada. A revisão independente encontrou duas regressões (maximização com auto-hide e propriedade de atalho); ambas foram reproduzidas com testes falhando e corrigidas.

A matriz visual/integração Windows acima permanece pendente. Não foi executado o script PowerShell neste Mac, nem disparado workflow remoto ou publicado release. A publicação local usa o mesmo comando `dotnet publish` do script.
